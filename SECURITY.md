# Security approach

**Goal:** Claude can read Google Ads freely, but every change needs **a person approving that exact change**, and every new campaign starts paused. The ad data and the login stay between your computer and Google. No single control here is absolute: [Risks that remain](#risks-that-remain) lists what each can't stop.

This repo is the "light" setup: two local servers, and only one of them can change anything.

| Server | Can change the account? |
|---|---|
| `google-ads`, [Google's official Google Ads MCP server](https://github.com/googleads/google-ads-mcp) | No. It is read-only by design. |
| `google-ads-builder`, this repo's `builder/` | Only through its three change tools, and only after a click on **Approve** in its own window. |

## Controls

### 1. No third-party service in the data path
Both servers run **on your computer**. Requests go straight from it to Google (`googleads.googleapis.com`), signed in as you. No hosted connector sees your ad data or your login.

### 2. Google's own server for reading
Questions about the account go to Google's official server, which has no tools that change anything.

### 3. Your own permissions, nothing more
Claude acts as **the signed-in Google user**. It can do exactly what that user can do in the Google Ads UI, and no more. Give team members **Standard** access rather than **Admin** for a tighter limit.

### 4. Login stored privately, never shared
- The sign-in asks only for the Google Ads scope (`https://www.googleapis.com/auth/adwords`): no Gmail, Drive or anything else.
- `scripts/signin.py` saves the login in `~/.config/google-ads-mcp/` (Windows: `%USERPROFILE%\.config\google-ads-mcp\`). On a Mac it sets the folder to `700` and the files to `600`, so only your user can read them. On Windows the folder sits in your user profile, which Windows keeps private to your account and the computer's administrators.
- `.gitignore` blocks every credential file name from this repo. Each person makes their own OAuth client in their own Cloud project and their own `builder.toml` with `scripts/make_settings.py` (or a team shares them privately), never through GitHub.
- The example Claude Code settings deny Claude's Read tool on that folder: `Read(~/.config/google-ads-mcp/**)`.
- To revoke at any time, go to [myaccount.google.com/permissions](https://myaccount.google.com/permissions).

### 5. Sign-in limited to the company
If you set the OAuth app's audience to **Internal**, only accounts in the company's Google Workspace can sign in.

### 6. Limited damage per day
Google's API access levels cap how many operations a Cloud project can make each day (see [access levels](https://developers.google.com/google-ads/api/docs/api-policy/access-levels)). New campaigns are always created **paused**, and no tool here can switch a campaign on.

### 7. The approval window on Windows
On Windows the builder runs Windows PowerShell by its absolute path under System32, which it asks Windows itself for (`GetSystemDirectoryW`; the `SystemRoot` and `PATH` variables are never trusted), with `-NoProfile -ExecutionPolicy Bypass -STA -Command` and **one fixed script** (`POWERSHELL_SCRIPT` in [`confirm.py`](builder/src/gads_builder/confirm.py)). PowerShell starts in System32 with a minimal environment: the window's title, text and timeout, `SystemRoot` and `windir` set to the real Windows folder, `COMSPEC`, `TEMP`, `TMP`, `USERPROFILE`, `LOCALAPPDATA`, `APPDATA` and `PATHEXT`. It never gets `PATH`, `PSModulePath`, `__PSLockdownPolicy` or the `COR_*` profiler variables, which could load other code into the window.

- **No plan text in the command.** The title and the text never go into the script or onto the command line. They travel as base64 of their UTF-8 bytes in environment variables, so no quote, `$`, backtick, line break or Arabic or Persian letter can change what PowerShell runs. No temporary file is written, so nothing can swap the text between writing and reading. The tests check the command for hostile text, and CI opens the real window on Windows with such text.
- **The window** is a WinForms form that stays on top, titled by the server, with a read-only, scrollable text box holding exactly the lines the Mac dialog shows (at most 45, each at most 120 characters, never wrapped).
- **Only a physical mouse click on Approve counts.** The script compiles a fixed piece of C# (`GUARD_SOURCE` in `confirm.py`, carried in the script as base64; it never holds plan text) that watches the mouse with a low-level hook. A click on **Approve** counts only if the hook saw a physical left button down and up on Approve, the up at most 300 ms before the click, with Approve where it stood when it was armed and no other window covering it there. Windows marks input that a program makes up as *injected* (`LLMHF_INJECTED`, `LLMHF_LOWER_IL_INJECTED`), and the hook refuses it. So these never approve:
  - a click made with `SendInput` or `mouse_event` by any program running as you, including a PowerShell that Claude starts;
  - `WM_LBUTTONDOWN`/`WM_LBUTTONUP` or `BM_CLICK` messages posted to the window: they don't pass through the hook at all;
  - the keyboard. **Cancel** is the form's Accept and Cancel button and has the focus, so Enter and Esc cancel. **Approve** has no tab stop, but the arrow keys can still move the focus to it. That is harmless: Space or Enter on a focused button only raises its Click event, and the window waits for a mouse click, so no key approves. UI Automation's *Invoke* does the same as Space.
- **Armed after 1.5 seconds.** Approve is disabled for the first 1.5 seconds after the window shows, and again for 1.5 seconds after the window moves or changes size. A window that appears, or is moved, under the pointer can't catch a click meant for something else.
- **One window at a time, across all Claude Code sessions.** The script takes the named mutex `Local\GadsBuilderApproval` without waiting. If another approval window holds it, nothing opens and the change is refused: "Another approval window is already open on this computer".
- **Fails closed.** If Windows PowerShell is missing or locked down (Constrained Language Mode, AppLocker, Device Guard), `Add-Type` can't compile the guard, or the hook can't start, no window opens and the change is refused with "The approval window couldn't start on this PC: …". That is not counted as a Cancel. CI checks it by running the script in Constrained Language Mode.
- **Timeout.** A timer closes the window as Cancel after the same 60 seconds as the Mac dialog. The process itself is stopped 30 seconds later.
- **The answer.** After the window closes, the script prints `APPROVED` or `DECLINED`. The builder counts it as approval only if PowerShell exits with code 0 **and** its output, trimmed, is exactly `APPROVED`. `DECLINED` or a timeout is a No. Any other result means the window failed, which is never an approval either.
- **What it can't stop.** Software with more power than an ordinary program: a kernel driver (some remote-control, macro and "virtual mouse" tools install one) makes input that Windows treats as physical, and a helper with UIAccess rights or running as administrator can act on the window in ways the hook doesn't see. Also, any program running as you can skip the window altogether by using your Google login directly (see [Risks that remain](#risks-that-remain)). The guard stops programs and scripts that fake a click, not every program on your PC.

CI runs the real window on Windows: it times out as a No with hostile text, a test program's posted clicks and `SendInput` click on Approve are refused, a second window is refused while one is open, and a locked-down PowerShell reports that the window couldn't start.

### 8. The campaign builder's gates
A change reaches Google only if **every** gate below passes.

| Gate | What it stops |
|---|---|
| The builder's own approval window (on macOS a native dialog; on Windows a WinForms window, see below) | Any change without a click, in **any** Claude Code mode. The server builds the text itself from the loaded plan, the config and the live account, never from Claude's arguments: account, tool, fingerprint, campaign, budget and over-cap flag, bidding, for a Search campaign its networks (Google Search only, or with search partners) and how many locations and languages, and counts; for a Demand Gen campaign also every conversion goal it bids on, how many other account goals it switches off, each ad group's channels and how many locations, languages and audiences it has, and that optimized targeting is not sent (Google's default may apply); for a Performance Max campaign every conversion goal it bids on, how many other account goals it switches off, how many locations and languages, the business name and how many logos, counts, each asset group's final URL and the fixed settings; for an image upload every file by its full path; for asset updates the live status ("LIVE: takes effect immediately"), how many items are added and removed, then every removed item and every added item. Free text is in quotes, and invisible or format characters are flattened. If the list doesn't fit in one window (45 lines), the change is refused, never cut: split the plan. After **Approve**, an asset update's ad and campaign (or the account's conversion goals, for a Demand Gen or Performance Max campaign) are read again, and the change is refused if anything differs from what the window showed. Only **Approve** counts, and on Windows only a physical mouse click on it (see section 7): Cancel, Enter, Esc, closing it, the 60-second timeout or an error once it is open is a no, and nothing is claimed or used up, until the third no for a plan, which refuses that plan for good (the count is read from its `approvals.jsonl`, so checking again or a restart doesn't reset it): draft a new plan. A window that couldn't open at all (a missing or locked-down PowerShell or osascript) is refused with its own message and is not counted as a no. Only one window opens at a time, across all Claude Code sessions on the computer (on Windows a named mutex, on a Mac an exclusive lock file in `~/.config/google-ads-mcp/`); a change tool called while one is open is refused at once, never queued. It can't be switched off in the config, and the offline tests can't open it (except the opt-in Windows tests that CI runs, which the window's own timer cancels). On any other system, such as Linux or WSL, no window can open, so every change is refused with a message saying so, before anything is read from Google. |
| Claude Code's prompt (`permissions.ask` in [config/claude-settings.json.example](config/claude-settings.json.example)) | A second look at the same arguments: account, fingerprint, campaign name, budget and over-cap flag; for asset updates the live status and every added or removed item (a new image by its full path). The builder validates the arguments strictly: one of the wrong JSON type (such as `"true"` or `0` for `over_cap`, or `"300"` for `daily_budget`) is refused, never coerced. |
| The summary must match the plan exactly, and the names in it are checked against Google | A plan or config changed after you read its summary, a label that misnames a location, language, conversion or asset, or a plan not made by `draft_plan` |
| Google's check-only pass, held **in the server's memory** for the **exact request bytes** | A hand-written "check passed" file, or an image swapped between check and send. A check is single-use. |
| No fake lines in the summary or the prompt | Free plan text they show (campaign name, ad text, template, `brief.sources` and `brief.names` values, deep links, image paths, an asset update's items) is an error if it has line breaks, other control characters or bidi controls; other shown values must match an exact pattern (ASCII digits) or an allow-list. Campaign and ad group names, and a Demand Gen ad's business name, also may not hold invisible characters or blank-looking letters (the Hangul fillers, the blank Braille pattern), so a padded name can't pass for another. Any error stops check_plan, so a checked plan can't add a line such as a different budget. |
| A one-time apply claim (`O_EXCL`), under a lock | Double applies, and blind retries after an unknown outcome such as the connection dropping mid-send |
| Allowlists of operation types and fields, and the plan's values | Anything except the operations a plan kind needs: no removes, references checked, and each kind of operation only with the one action its compiler uses (a create; an update only for a Demand Gen or Performance Max conversion goal and an asset update's ad). The values the builder hard-codes are pinned: the campaign status PAUSED; ad group, Performance Max asset group, ad and keyword statuses as the compiler sets them (ENABLED, inside the paused campaign; no other criterion, and no asset group link, may carry a status); the EU political ads declaration (no EU political ads); the budget's standard delivery; and a Search ad group's type (standard Search). A new budget is explicitly not shared, and no criterion but a keyword may be negative (no excluded locations). **Every field the request sets, at every depth, must be one the builder's compiler sends for that plan kind** (for an asset update, for that ad type), and so must each operation's own fields and update mask: a tracking template, a final URL suffix, an opted-in automation, a bid modifier, a budget period, an ad group bid override or a policy exemption is refused. The lists are per operation type and, where kinds differ, per kind of asset or criterion (a sitelink, callout, snippet, text, image, YouTube video or call-to-action asset; a location, language, user list, keyword or negative keyword; a Performance Max audience or search theme signal), so a field one kind carries can't ride on another (a final URL on a callout, a name on a call to action, a status on a negative keyword). A field number the installed library doesn't know (an unknown field, which protobuf keeps and sends) is refused at every depth. **The values are compared with the plan, in order**, so a compiler bug can't send something other than what the person approved: the names; an App campaign's app, store, type and subtype, conversion actions, locations and languages, and its ad's type, texts, images, videos and deep links; a Search campaign's locations, languages, keywords and negative keywords (text and match type), each ad's ad group, texts and paths, and the sitelinks, callouts and snippets and the kind each is linked as; every new image (the plan's file, with the file's bytes, read again, and its compiled name) and new YouTube video; an upload's files; and an asset update's lists (the ad's items the plan keeps, then the added ones, for one update of the planned ad) under exactly the mask paths it sends, and, checked again from the plan alone, without the compiler's helper, every removed item gone and every added one there. Every Search ad's and sitelink's final URL is exactly the planned one, on the allowed domains. The bidding is checked against the plan: the strategy, its target CPA, max CPC ceiling and impression-share settings, an App campaign's goal and each Search ad group's manual bid. A Demand Gen campaign's maximize-conversions and maximize-clicks settings must be empty (no target, no CPC ceiling: Google refuses both on a new Demand Gen campaign; a target goes with TARGET_CPA). A Search campaign is never on the Display Network, is on search partners exactly as planned, and its criteria, ad groups, keywords, ads and asset links may only point at parts created in the same request. A Demand Gen campaign must have every fixed setting present in the request (upgraded targeting, the location option "people in or regularly in", the EU political ads declaration, no network settings; set by the builder; for the location option, Google's check-only run accepts the request and `quality_report` reads the setting back after creation); its only updates are its own conversion goals (exactly the plan's on, every other account goal off, nothing but the biddable flag; set by the builder; Google's check-only run accepts the request and `quality_report` reads the goals back after creation); each ad group has exactly its planned channels (never third-party Display or Maps), exactly its planned locations, languages and user lists, and no demographic expansion (the channels and the expansion setting are confirmed by Google's check-only run), and the builder never turns optimized targeting on (it can't be sent as off; see Risks); each ad is an image or video ad with only its own fields, its planned name and ad group, its planned headlines, long headlines, descriptions and business name, exactly its planned final URL on the allowed domains, exactly its planned image in every image and logo slot, and every generated creative opted out (set by the builder; for the opt-outs on both ad types, Google's check-only run accepts the request and `quality_report` reads the settings back after creation; the ad names are confirmed by Google's check-only run); the campaign, budget and ad group names, the new YouTube videos and calls to action, and each video ad's, are the plan's; and every asset an ad uses is new in the request or already in the account. A Performance Max campaign must have brand guidelines on, exactly the asset automations the builder opts out of (final URL expansion, generated text, enhanced videos, image enhancement, automated video crawl), each present and opted out, the location option "people in or regularly in" and the EU political ads declaration; its bidding (maximize conversions or maximize conversion value, with exactly the plan's target CPA or target ROAS) and its conversion goal updates are checked like Demand Gen's; each asset group is ENABLED with exactly its planned final URL on the allowed domains and its planned display path; and the names, locations and languages, the new texts, images (the plan's files: bytes and names), YouTube videos and calls to action in order, the brand links and every asset group link slot by slot in order (each the planned existing asset or the new asset made for that text or file), and each asset group's audience signal and search themes are the plan's; every asset a link uses is new in the request or already in the account, and every new asset is linked. |
| Always paused | Campaign status is hard-coded, with no switch-on tool |
| Budget cap (private) | Budgets above the cap need the exact amount; above 3× the cap they're always refused |
| Local rules | The account currency, allowed apps, deep links on the right platform and under the app's allowed prefixes, **final URLs and sitelinks only as https on the allowed `domains`** (no user name, port, backslash or invisible characters), text limits, editorial rules, blocked words (a keyword may name a competitor, ad text may not), broad match only with smart bidding, never a Demand Gen or Performance Max app goal, at most 50 audiences per Demand Gen ad group, a YouTube video in every Performance Max asset group and a short description in each, at most 20 images per Performance Max asset group (the three shapes together) and 5 logos per campaign (square and landscape together; Google's limits), image shapes and Google's smallest sizes per list, and names of at most 255 characters, including the budget, ad group, asset and Demand Gen ad names made from them |
| Live reads in `check_plan` (again before the window opens) | A plan whose currency isn't the account's, a location, language, audience or conversion action that doesn't exist, a Demand Gen or Performance Max conversion goal the account doesn't have, a Performance Max audience signal that isn't an enabled account-wide audience, or a Demand Gen budget below Google's minimum for the currency (read from Google; no answer is a refusal) |
| Landing page checks | `check_landing_pages` fetches only https pages on the allowed domains whose host resolves to public internet addresses (checked before every redirect hop; a VPN's fake-IP range 198.18.0.0/15 is also allowed, with a note in the result, and every other private, loopback or link-local address is refused), follows a redirect only while it stays on them, reads at most 2 MB per page within 20 seconds (120 per call), runs no JavaScript and changes nothing. Its results show at most 500 characters of a URL and only the host of a redirect it refused |
| Plans folder only | Plans outside the configured `plans_dir` in `builder.toml`: each must be in a folder `draft_plan` made directly inside it, after resolving symlinks, junctions and `..`, and that folder's parent must be the very same folder on disk as `plans_dir`. On Windows, path names compare without regard to letter case, as Windows does |

Every plan, check and result is saved in the plan's folder: `plan.json`, `summary.md`, `checks.jsonl` (with each failed check's errors), `approvals.jsonl` (each answer in the approval window, with exactly the lines it showed), `applying.json`, `result-*.json` and `attempt-*.json` (each real request Google refused or whose outcome is unknown). Tests run offline behind a network guard. The live check-only suite covers App, Search and Demand Gen campaigns and is run on the real account before each release, behind a guard that fails any real change, so nothing is created. Its Performance Max tests (`-k pmax`) passed on the real account on 2026-10-22: Google accepted the asset automation opt-outs, brand guidelines with the business name and logos, a target CPA and a target ROAS on a new campaign, an audience signal, two asset groups and a template copy. Dependencies are pinned in `builder/uv.lock`.

## Risks that remain

| Risk | What to do |
|---|---|
| Approving a wrong change by habit | Read every window: account, campaign, budget, every item. Click Cancel if anything looks off. |
| Claude Code's auto mode skips its own `ask` prompts | The builder asks in its own window in every mode. Prefer the default mode for ad work anyway. |
| **The direct route around every gate.** In auto mode, or after you approve a command without reading it, Claude could run the `google-ads` Python library itself with `google-ads.yaml` from the login folder, which your user can read, and change the account directly. That skips every gate above, including the approval window. | Read every command before approving it, and don't use auto mode for ad work. Keep the `Read` deny rule from the example settings. On a Mac (and Linux), turn on Claude Code's command sandbox, add the login folder to `sandbox.filesystem.denyRead`, and set `sandbox.allowUnsandboxedCommands` to `false`. Claude Code has no command sandbox on Windows itself, so there the careful reading of every command is the protection. |
| Something with more control of your computer than an ordinary program could click **Approve**: a computer-use or remote-control tool, on Windows a kernel driver or a UIAccess or administrator helper (fake clicks from ordinary programs are refused, see section 7), on a Mac an app with Accessibility permission | Don't run these while working on ads. On a Mac, a script can click a dialog's button only if the app it runs in has Accessibility permission, and Claude's commands run inside the app that runs Claude Code. So never give Terminal, iTerm or VS Code Accessibility permission (System Settings → Privacy & Security → Accessibility). |
| Claude could edit the builder's code or Claude Code's settings | Review changes to this folder and to your Claude Code settings. |
| Google's official server is installed from its GitHub repository at its latest version, and its login (`adc.json`) has the same Google Ads scope as the builder's | It is Google's own code and read-only by design. To control updates, pin it to a commit you reviewed: `git+https://github.com/googleads/google-ads-mcp.git@<commit>`. |
| The builder's own dependencies | They are pinned in `builder/uv.lock`, and the server starts with `uv run --frozen`. |
| Demand Gen's optimized targeting can't be sent as "off" through the API (Google's field has no explicit value), so Google may switch it on | The builder never turns it on, and the approval window says it is not sent. `quality_report` reads it back after creation and lists it in `to_review`; switch it off in Google Ads before switching the campaign on. |
| Performance Max image extraction (images taken from the landing page) follows an account setting the API can't change, and Google may add assets of its own (such as generated videos or sitelinks) | `quality_report` reads both back after creation and lists them in `to_review`; switch image extraction off and remove unwanted assets in Google Ads before switching the campaign on. |
| Text in ad data or on web pages (search terms, ad copy, landing page titles and URLs) could try to instruct the AI ("prompt injection") | The playbook tells Claude to treat it as data. The approval window still catches any change, so never approve a change you didn't ask for. |
| A landing page's DNS answer could change between the address check and the connection (DNS rebinding); behind a fake-IP VPN (198.18.x.x answers) the address check can't see the real address at all | `check_landing_pages` only reads: plain GET requests without cookies or logins, to the allowed domains only. A result that went through the fake-IP range says so in its `note`. |
| `generate_image` runs Codex on your computer | Codex gets the prompt on stdin, never as a command-line argument, and runs in its read-only sandbox. On Windows only `codex.exe` runs, by its full path: never a `.cmd` or `.bat` file (`cmd.exe` would read their arguments by its own rules), and the lookup never takes a `codex.exe` from the folder Claude Code was started in (see [SETUP.md](docs/SETUP.md#optional-images-with-codex)). |
